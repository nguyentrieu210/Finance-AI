# G01 upload lifecycle — technical draft
No object storage implementation, live credentials or real file ingestion is included here. Authorization, malware scanning, provider integration and retention are gated. Proposed defaults are technical pilot limits (25 MiB/file, 100 MiB/dossier; 200 pages/dossier after parse). Production policy may be stricter.

1. Create document intent: validate declared MIME allowlist, positive bytes, lowercase SHA-256, filename metadata, scope and current editable dossier revision. Under quota lock reserve bytes across all outstanding and finalized documents. Return stable intent metadata only, never a signed URL in this receipt. Initial grant generation 0; state PENDING_UPLOAD. No readable original exists.
2. Issue grant: POST documents/{document_id}/upload-grants, authorized scoped requester, current parent version, new idempotency key. Increment generation atomically, bind generation to current dossier revision and a server-generated private staging key, declared bytes/digest/MIME, expiry. Return generation, short-lived PUT URL, required Content-Type and x-amz-checksum-sha256 headers. Provider capability test must prove signed write constraints, no overwrite of promoted originals and bounded upload size; if provider cannot enforce bounds use a bounded upload gateway. TTL target 5 minutes, server policy capped. Replay the same immutable grant receipt only while valid and current; expired/superseded grant -> 409 UPLOAD_GRANT_INACTIVE, no new URL from replay. New grant requires new key and current parent version; invalidates old generation even if URL remains usable for its isolated staging key. No signed URL logs or durable plaintext receipt; protected grant metadata/secret handling is E05 implementation.
3. PUT to private staging only; client completion is not proof. Finalize references current grant generation plus expected digest. Verify exact immutable staging object version with server-computed hash and length; detect MIME from bytes; compare declared values. Promote/copy exact verified bytes to a new immutable quarantine key using provider preconditions; no mutable staging alias as original. Recheck current generation, expiry, revision, auth, quota and version inside final transaction; atomically attach immutable ref, consume reservation, queue scan and audit. Avoid network calls in DB transaction; recovery reconciles orphan objects and unsuccessful DB commits. Race/expiry fails closed. Replayed completed finalize returns original job receipt after current authorization. No OCR/download before clean, except isolated scanning service.
4. Expired intents remain pending until authorized cleanup/expiry policy releases quota. Cancellation and supersede invalidate grants and staging references; sealed revision immutable. Never delete under legal hold. Reaper is fenced and must not delete promoted bytes; old staging keys never reused.

Guard code in crates/shared/src/upload_contract.rs validates metadata, quota arithmetic and generation/expiry only. No claims of actual object-store enforcement, transaction locking, MIME detection or malware scan. Upload grant refresh, cancellation, retention and size controls need engineering/security review and real E05 tests.
